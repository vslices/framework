# VSIR editable projections

This note records an experimental design direction for VSlices Intermediate Representation tooling.

The intent is to preserve manual control over generated projections while still allowing automation to detect when a projection has diverged from its source VSIR.

## Projection files are editable

A VSIR source file and its C# projection should be colocated with the application code they describe.

Example:

```text
ActivateAccount.feature.vsir
ActivateAccount.feature.vsir.cs
```

The `.vsir.cs` file is not conventional generated code and must not be treated as read-only.

Manual editing is explicitly supported because:

- VSIR may not be expressive enough for every implementation detail;
- an automated interpretation may fail to represent the intended behavior correctly;
- low-level or performance-sensitive code may require constructs that VSIR deliberately does not model;
- developers must always retain the ability to leave the abstraction and write C# directly.

Therefore, a projection is better understood as an **editable projection** rather than an owned generated artifact.

```text
*.vsir
   |
   v
projection
   |
   v
*.vsir.cs
   ^
   |
human refinement
```

Manual divergence is information, not corruption.

## Never overwrite an edited projection silently

Before regeneration, tooling must determine whether the current `.vsir.cs` file still matches the projection produced during the previous generation.

If it does not match, automatic replacement is prohibited.

The tool should instead:

```text
1. Detect the divergence.
2. Preserve the current implementation.
3. Report the divergence to the developer.
4. When possible, analyze the difference.
5. Suggest a VSIR modification that would represent the manual change.
```

A suggestion is not permission to rewrite the VSIR automatically.

Some manual changes may intentionally remain outside VSIR expressiveness.

For example, specialized allocation behavior, `Span<T>`, `stackalloc`, `MemoryMarshal`, unsafe code, SIMD, platform-specific code, specialized SQL, or other performance-sensitive implementation details may be legitimate projection drift that should simply be preserved.

## Projection fingerprint

The initial detection mechanism can be deliberately simple.

When VSIR is projected into C#, the projection is normalized and hashed.

Conceptually:

```text
VSIR
  |
  v
projection
  |
  v
normalized C#
  |
  v
SHA-256
  |
  v
projection fingerprint
```

If a projection originally produced normalized content with fingerprint `ASDF`, a later regeneration first normalizes the current `.vsir.cs` and calculates its fingerprint.

```text
current fingerprint == stored projection fingerprint
    => projection has not been manually modified

current fingerprint != stored projection fingerprint
    => projection drift exists
    => DO NOT OVERWRITE
```

This makes drift detection independent from the non-determinism of any AI involved in earlier semantic interpretation.

## Normalization is required

The fingerprint should not be calculated from raw text.

Formatting-only changes should not count as manual semantic divergence.

For C#, normalization should ideally be based on Roslyn syntax rather than ad-hoc whitespace removal.

The normalized representation should ignore non-semantic trivia such as:

```text
indentation
line endings
whitespace
formatting trivia
comments that are not part of VSIR metadata
```

while preserving semantic changes such as:

```text
different invocations
different arguments
different conditions
additional operations
different types
different control flow
```

The projection metadata itself must be excluded from the content used to calculate the projection fingerprint; otherwise the file would indirectly contain the hash of a representation containing its own hash.

## VSIR source fingerprint

The same idea should be applied to the source VSIR.

Because the current VSIR serialization is YAML, the source fingerprint should be computed from a canonical semantic representation rather than raw YAML text.

Conceptually:

```text
VSIR YAML
   |
   v
parse
   |
   v
canonical VSIR model
   |
   v
deterministic serialization
   |
   v
SHA-256
```

Thus harmless changes such as mapping order or formatting need not make the semantic source appear changed.

## Two fingerprints

A projection should track at least two values:

```text
source fingerprint
projection fingerprint
```

Possible metadata:

```csharp
// <vsir
// source="ActivateAccount.feature.vsir"
// source-hash="sha256:..."
// projection-hash="sha256:..."
// />
```

Do not use `<auto-generated />`, because that communicates the wrong ownership model and may cause analyzers or IDE tooling to treat the file as non-human code.

The metadata records provenance; it does not prohibit editing.

## Projection state

Comparing the stored fingerprints with the current normalized source and implementation gives four useful states.

```text
Source hash   C# hash   State
-----------   -------   ----------
same          same      Clean
changed       same      Stale
same          changed   Drifted
changed       changed   Conflicted / review required
```

### Clean

Neither source nor projection has changed since the last projection.

No action is required.

### Stale

The VSIR changed but the C# projection remains untouched.

The projection may be safely regenerated under the current lowering rules.

### Drifted

The VSIR is unchanged but the C# projection has been manually edited.

The implementation must be preserved.

Tooling may analyze the difference and suggest whether the VSIR can represent the manual change.

### Conflicted

Both VSIR and C# changed since the last known projection.

Automatic replacement is prohibited.

The tool should generate the new expected projection in memory, compare it against the current implementation, report the relevant differences, and require review.

## Fast path and slow path

Fingerprint comparison provides an inexpensive fast path.

```text
FAST PATH

normalize current implementation
        |
        v
compare fingerprint
        |
        v
unchanged
        |
        v
safe regeneration when source changed
```

Only a mismatch requires deeper analysis.

```text
SLOW PATH

fingerprint mismatch
        |
        v
projection drift
        |
        v
structural comparison
        |
        v
diagnostic
        |
        +--> possible VSIR recommendation
        |
        +--> preserve opaque manual implementation
```

This allows intelligent analysis to remain exceptional rather than being required for every generation.

## Difference analysis and feedback to VSIR

When a projection differs from the expected lowering, the automated tooling should attempt to describe the divergence structurally.

Example:

```text
VSIR projection:
    Accounts.Read(id)

Current implementation:
    Accounts.ReadProjected(id)
```

A useful diagnostic could be:

```text
Repository operation changed:
    Read -> ReadProjected
```

When the difference maps cleanly to an existing VSIR concept, the tooling may suggest a source change:

```yaml
from:
  repository: Accounts
  operation: ReadProjected
  arguments:
    - input
```

This creates a feedback loop:

```text
VSIR
  |
  v
Projection
  |
  v
Human modification
  |
  v
Difference analysis
  |
  v
Suggested VSIR refinement
  |
  v
VSIR
```

The recommendation should remain optional.

A projection may intentionally contain behavior that VSIR cannot or should not represent.

## Authority model

The relationship between VSIR and its projection should avoid the usual "generated source owns the code" model.

A useful distinction is:

```text
VSIR
    source of truth for the intended semantic projection

.vsir.cs
    authoritative executable implementation
```

The implementation may intentionally diverge from the projection.

The tooling's responsibility is to detect and explain that divergence, not erase it.

## Possible terminology

The difference between the current implementation and the expected VSIR projection can be called **Projection Drift**.

Future tooling may classify drift more precisely, for example:

```text
Exact
    implementation matches the VSIR projection

Formatting-only
    syntax representation differs without semantic change

Compatible drift
    implementation differs but still satisfies the represented contract

Representable drift
    the manual difference appears expressible in VSIR

Opaque drift
    the implementation uses behavior outside current VSIR expressiveness

Conflict
    both source intent and manual implementation changed in overlapping areas
```

These categories are exploratory and do not need to be implemented in the first version.

## Initial implementation rule

The first manual operator does not need sophisticated merge logic.

It only needs a strong safety rule:

> Normalize, fingerprint, and compare before writing. If the current projection fingerprint differs from the stored projection fingerprint, do not overwrite the file.

Everything beyond that can evolve incrementally.

The system should prefer preserving human work and returning a diagnostic over guessing how to merge or reinterpret it.
